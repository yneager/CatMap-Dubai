====================================================================================================================
## 1. Goal

Build **CatMap Web** in `web/`: a Progressive Web App that is a **near 1:1 copy of the Android app**
(`app/src/main/java/com/catmap/dubai/`). It's for iPhone users, who open it in Safari and use "Add to Home Screen" so
it runs full-screen like an app. It must also work in desktop browsers and Android Chrome.

"1:1" means:
* the same screens, in the same order and navigation;
* the same features, fields, limits, wording, colours, icons, shapes and states (loading, empty, error, offline);
* the same data.

The web app talks to the **same Firebase project** (`catmap-dubai`) as the Android app, with the same Firestore
documents, under the same security rules (`firestore.rules`). Concretely:
* a post created on the web must look and behave exactly like one created on Android, and the reverse;
* an Android user and a web user can chat with each other;
* the admin can moderate from either app.

**The Android app is the specification.** When this brief and the Kotlin code disagree about behaviour, the Kotlin
code wins. Read the matching Kotlin file before building each screen or repository.

The only deliberate differences are the platform adaptations in section 9.

## 5. Tech stack (decided)

Make `web/` its own npm project, with its own `package.json` and lockfile.

* **Build and language:** Vite, React (function components and hooks) and TypeScript in `strict` mode.
* **Routing:** React Router, in browser-history mode.
* **Firebase:** the modular Firebase JS SDK (`firebase/app`, `firebase/auth`, `firebase/firestore`, and
  `firebase/storage` only for the Blaze video path).
  * Firestore uses `initializeFirestore(app, { localCache: persistentLocalCache({ tabManager:
    persistentMultipleTabManager() }) })` for offline support.
  * Auth uses `indexedDBLocalPersistence`.
* **Map:** MapLibre GL JS.
* **PWA:** `vite-plugin-pwa` (Workbox) for the manifest and service worker.
* **Local storage:** `idb-keyval`, or a tiny IndexedDB wrapper, for drafts, caches and settings that must survive.
* **Poster QR code:** a small QR library such as `qrcode`.
* **Fonts:** self-hosted through `@fontsource` packages, so the app works offline: Roboto (the font Compose uses on
  Android) and Noto Sans Arabic for Arabic. Fall back to the system font stack.
* **Quality tools:**
  * `vitest` for unit tests;
  * `@playwright/test` for end-to-end tests, with the **WebKit** project (as the iPhone stand-in) and Chromium;
  * ESLint with the TypeScript and React Hooks configs;
  * `tsc --noEmit` in the checks.
* **Styling:** plain CSS (CSS Modules, or one token stylesheet plus per-component CSS). No Tailwind, no UI kit.

**npm scripts:**
* `dev` and `dev:emulators`: the Vite dev server against the local emulators;
* `build`, `preview`;
* `lint`, `typecheck`;
* `test` (vitest) and `test:e2e` (Playwright, against the emulators);
* `screens`, which writes the screenshot set from section 12.

Port each Kotlin repository to `web/src/data/<Name>Repository.ts`, with the same responsibilities and function names
where sensible:

| Admin | Admin, AdminAnalytics, Moderation |

**8.1 Document shapes must match exactly.**
* Same collection names (`data/Firestore.kt`, `Col`), field names, nesting and **document ids**.
  * Deterministic ids include `{postId}_{requesterId}`, chat id = sorted uids joined with `_`, the review id = the
    booking id, `usernames/{lowercase}`, and notification dedupe ids `msg_{chatId}`, `lost_{postId}`,
    `match_{postId}`, `upd_{postId}`, `stale_{postId}_{window}`.
  * Find every other deterministic id in the Kotlin code.
* **Types must match the Kotlin models.**
  * Kotlin `Long` fields (timestamps in epoch milliseconds, counts, `areaRadiusM`, `reward`, `rate`, ratings and so
    on) must be written as **whole numbers** (`Math.round`).
  * `Double` fields stay numbers.
  * Android maps documents with `toObject()`, so a fractional value in a Long field breaks Android.
* **Timestamps:**
  * Use client milliseconds (`Date.now()`) wherever Kotlin uses `now()`.
  * Use `serverTimestamp()` exactly where Kotlin uses `FieldValue.serverTimestamp()`. One example is `lastPostAt` in
    `UserRepository.addStats`, which the rules compare with `request.time` for rate limiting.
  * Use `increment()` where Kotlin uses `FieldValue.increment`.
* **Writes:** use the same batching and transactions as Kotlin (`runBatch` → `writeBatch`, `runTransaction` →
  `runTransaction`). The rules often depend on fields being written together in one batch, such as post plus stats or
  update plus counter.
* **Input limits:** apply the same trimming and limits before writing, for example name 60, description 2000,
  features 400, 6 photos, area radius 0–5000 m, reward 0–999999 (lost posts only), message lengths and username
  pattern `^[A-Za-z0-9_.]{3,20}$`. Find them in the Kotlin code.
* **Derived fields:** compute `keywords` (`PostRepository.keywords`) and `neighborhood` (`Dubai.nearest`) exactly like
  Kotlin, with the same splitting regex, minimum length and the cap of 80. Port `data/Neighborhoods.kt` verbatim.
* **Reading:** each model gets a `fromDoc()` that applies the Kotlin defaults for missing fields. Older documents lack
  newer fields, and the Kotlin defaults handle that.
* **Feed and lists:** keep the same queries and limits, for example the feed is `hidden == false`, ordered by
  `createdAt` descending, limit 400. Use one shared live feed subscription for the whole app, as Android does
  (`AppContainer`), not one per screen.
* **Listener errors:** show the shared error banner with Retry, like `AppErrors`. Expected permission errors right
  after sign-out stay silent.
* **Points, badges and stats** are client-managed on Android (`UserRepository.addStats`, `gamification/Badges.kt`).
  Port them exactly, with the same point values.

**8.2 Photos (Firestore blobs, like `data/ImageRepository.kt` and `util/ImageUtils.kt`).**
* **Storage:** `images/{id}` holds the full JPEG; `images/{id}_t` holds the thumbnail. Each document is
  `{ data: Bytes, ownerId, createdAt }`, both written in one batch, using `Bytes.fromUint8Array`.
* **Processing** (match Android):
  * Decode upright, applying EXIF orientation (`createImageBitmap(file, { imageOrientation: 'from-image' })`, with a
    fallback).
  * **Full image:** scaled to at most 1280 px on the long side, then re-encoded as JPEG to fit 650,000 bytes. Use the
    same loop: quality 85, minus 10 while above 55; then shrink to 0.8× and reset quality to 80.
  * **Thumbnail:** at most 360 px, quality 72.
  * **Analysis image:** at most 512 px, kept in memory for the analyser.
  * Re-encoding through a canvas strips EXIF, including GPS. Keep it that way: it's a privacy requirement.
  * Accept HEIC from iPhones when the browser can decode it (Safari can). Otherwise show the same "couldn't read this
    photo" error Android shows.
* **Reading:**
  * Feeds and cards always use `{id}_t`, falling back to the full image the way Kotlin does.
  * Keep a memory LRU of object URLs, plus a persistent cache in IndexedDB or the Cache API with the same 40 MiB /
    24 h policy as `ImageDiskCache`.
  * Lazy-load images (IntersectionObserver).
* **Deleting:** delete both documents and evict the caches.

**8.3 Accounts (`data/AuthRepository.kt`, `UserRepository.kt`, `DemoAccounts.kt`).**
* **Register:** email, password, username and display name. Mirror Android:
  * the same validation (password at least 8 characters, username pattern, username free);
  * the same batch: `usernames/{lower}` + `users/{uid}` + `users/{uid}/private/account`;
  * the welcome notification;
  * delete the auth user if creating the profile fails;
  * send the verification email.
* **Verify:** the VERIFY screen with resend and "I've verified" (reload, then refresh the ID token).
* **Login:** by email, or by username.
  * Demo usernames are listed in `DemoAccounts.kt`, with the domain `demo.catmap.test`.
  * Other usernames are looked up through `usernames/{name}.loginEmail`.
  * Show the same errors as Android.
* **Profiles:** port `ensureProfile` and `ensureDemoProfile`. The admin role comes only from the `catmapAdmin` custom
  claim, read from the ID token.
* **Forgot password:** the same screen.
* **Logout:** clears the demo vault.
* **Delete account:** port the whole of `deleteAccount` and `CommunityAccountCleanup`, in the same order:
  re-authentication with the password, transactions, chunked batches, and the profile removed last.
* **Demo account switcher** (Settings → Demo accounts; shown only when signed in as a demo account with a saved
  password):
  * Android keeps the shared demo password encrypted with an Android Keystore key. On the web, encrypt it with
    **WebCrypto AES-GCM** using a **non-extractable** `CryptoKey` stored in IndexedDB, and keep only the ciphertext and
    IV.
  * Never put the password in localStorage in plain text, in logs or in URLs.
  * Switching signs straight into the next account, as Android does (no sign-out in between). Handle the same error
    cases ("sign in again", "demo account missing").

**8.4 Notifications (`data/NotificationRepository.kt`, `notifications/`).**
* Port `send()` exactly: the recipient inbox `users/{uid}/notifications`, deterministic dedupe ids, params and route,
  create-only.
* Every place Android sends a notification, the web sends the same one: lost nearby, possible match, post update,
  message, adoption, booking, review, moderation, rescue, welcome and so on.
* **Inbox screen:** the same layout and actions (mark read, mark all read, delete, open route), the unread badge on the
  bell (`ui/navigation/NotificationBell.kt`), and the same per-category switches in Settings.
* **While the app is open:** show an in-app snackbar or toast for new inbox items. Optionally use the browser
  Notification API, only after the person enables it in Settings and grants permission, and only while the app is
  open.
* Quiet hours (`notifications/QuietHours.kt`) suppress those pop-ups; the inbox still fills.
* No FCM or web push: Android also only has push on Blaze. Note it in the report as a future item.

**8.5 Settings (`data/SettingsRepository.kt`).** Store the same settings per device in IndexedDB:
* appearance: theme (system/light/dark), large text, language (English/Arabic);
* privacy: privacy level, share exact location;
* notifications: notification categories, quiet hours;
* map and filters: map mode (classic/modern), satellite, stations, heatmap, the filter layers, animals, distance, age,
  reward and "include older";
* app state: the "what's new" last-seen version, and the delivered-notification ids per user.

Language switching changes `<html lang dir>` instantly, without a reload if possible.

**8.6 AI same-animal check (`data/AiServer.kt`; read the whole file).** Port it exactly. It's how the owner's PC
receives photos:
* `health()` reads `config/aiWorker`: online only if `online == true` and `lastSeen` is within **390,000 ms**.
* **`run()`:**
  * Wait out the 1.2 s throttle after the previous job's `createdAt`.
  * `setDoc(aiJobs/{uid}, { ...fields, uid, status: 'pending', requestId: <uuid>, createdAt: serverTimestamp() })`.
  * Then `onSnapshot` that document until `answeredRequestId == requestId` and `status` is `done` or `error`.
  * Time out after **15,000 ms**; unsubscribe on finish.
* **`compare(query, candidates, labels)`:** `kind: 'compare'`, JPEG quality 85 crops, up to 8 candidates, labels cut
  to 60 characters.
* **`embed(crops)`:** `kind: 'embed'`, up to 16 images.
* Every failure returns `null`, so the caller falls back.
* Port `PostEditorViewModel.checkSameAnimal()` and the review-step UI:
  * the candidates are open, unhidden street posts of the same animal type, with photos, within 1 km, nearest 8;
  * the "same animal" card and the publish guard dialog ("Add to that post" / "Post anyway");
  * `addToExisting()`, which adds the photo as a SIGHTING update on the existing post instead of creating a new post;
  * the local fallback (`PostAppearance` similarity at least 0.85, top 3, marked "checked on this device").

**8.7 On-device analysis (`ai/CatAnalyzer.kt`, `ai/PostAppearance.kt`).**
* **No ML Kit on the web.**
  * Image labelling ("is this an animal?") and subject segmentation are Android-only.
  * Treat labelling as "not checked": never block the person.
  * Use the **centre-weight path** exactly as Android does on emulators (`centreWeights`). `cropSubject` becomes the
    same centre crop.
* **Port all the pure maths exactly:**
  * `describe`, `colourLayout`, `histBin`, `classify`, `coatColorFrom`, `stripeRate`, `patternFrom`, `breedHints`;
  * `Similarity` (visual, score, proximity, strength, average, valid);
  * `PostAppearance.describe` and `PostAppearance.similarity`, the 27-value fingerprint stored on posts.
* **Fingerprints must be compatible across platforms**, so web and Android posts match each other. Prove it:
  1. Add a small **web-side** fixture test using the PNG or JPEG images in `tools/testdata/` and `tools/seed/photos/`.
  2. To get reference values, write a tiny Kotlin JVM unit test **in a new file under `app/src/test/`**. It runs
     `PostAppearance.describe` and the analyser's descriptor on those images under Robolectric and writes JSON to
     `web/tests/fixtures/android-fingerprints.json`. This is the only allowed addition to the Android module; it is a
     test, not app code.
  3. Assert that web values are within a small tolerance, because decoders and scalers differ slightly. Use, for
     example, |Δ| ≤ 0.03 per value and cosine ≥ 0.98.
  4. Report the actual differences you measured.
* Port `ai/RecognitionEvaluation.kt` for Admin → Recognition test (section 9 says what changes there).
